# Twin Bishkek: бэкенд, карта, данные, ML

Куда класть: `src/twin_bishkek/` → ваш `src/`, `app/` → ваш `app/`, `tests/`, `pyproject.toml`.
Если в `src/` или `app/` уже есть файлы с такими именами, не перезаписывайте вслепую, сравните.

## Установка (из корня проекта, venv активирован)
```bash
pip install -e ".[api,app,dev]"      # + ".[osm]" для данных OSM
mkdir -p .streamlit && cp design/streamlit/config.toml .streamlit/config.toml
pytest                                # 17 проверок инвариантов модели
```

## Запуск
```bash
uvicorn twin_bishkek.api:app --reload --port 8000   # API + Swagger на /docs
streamlit run app/main.py                           # интерфейс с картой
```

## Данные
```bash
python -m twin_bishkek.data_download all --start 2023-01-01   # погода + воздух (CAMS) + OSM + склейка
OPENAQ_API_KEY=... python -m twin_bishkek.data_download openaq --start 2023-01-01
python -m twin_bishkek.data_download merge                    # → data/processed/hourly.csv
```
## ML
```bash
python -m twin_bishkek.ml train --horizon 24     # → models/pm25_h24.joblib + отчёт json
```
Следующие шаги: (1) наземные датчики вместо CAMS, (2) подстроить `P` в `simulator.py`
(фон зимой, `tp_summer_p95`) под реальные PM2.5, (3) заменить схему районов и улиц на OSM,
(4) суррогат: обучить быструю модель на тысячах прогонов `simulate()`.


## Настоящий город (OpenStreetMap)
Геометрия города лежит в `src/twin_bishkek/city_real.json`. Её делает `build_city.py` из слоёв OSM в `data/raw/osm/`
(нужны `boundary, roads, green, social, places, water`; скачиваются командами `data_download osm` и `osm_extra`).
Для сборки нужны ещё `scipy`, `scikit-image`, `matplotlib` (сайту и бэкенду они не нужны):
```bash
python build_city.py          # → src/twin_bishkek/city_real.json
python export_site_data.py    # → site/js/data.js (тот же город для сайта)
```
Сайт открывается на http://localhost:8000 (его отдаёт сам API из папки `site/`).
Пробки на карте: зелёный / жёлтый / красный / бордовый = потеря скорости по BPR: скорость ≥67% свободной / 45–67% / 28–45% / ниже 28% (V/C 1,0 / 1,25 / 1,5). Цвет по скорости, как в навигаторах и в 2GIS, а не по V/C напрямую.
Это расчёт модели, не онлайн-данные.

## Стройка и новая магистраль
У объектов (ЖК, ТЦ, Парк, Аттракционы) есть стадия: `ph = "build"` (строится) или `"done"` (построен). Во время стройки приезжает техника,
сужается проезд, появляется пыль, жителей нет; после стройки действует обычное поведение объекта. Параметры: `BUILD` и `WIDEN` в `city.py`
(и `P.build`, `P.widen` в `site/js/model.js`). Событие `events.widen = <id улицы>` даёт +50% ёмкости центрального участка улицы.
Пресеты: UC-06 «Стройка трёх ЖК в Джале», UC-07 «Новая магистраль вдоль Чуя». Все коэффициенты это допущения.

## Время суток
Параметр `hour` (0–23, `null` = в среднем за сутки). Профили в `TIME` (в `build_city.py` → `city_real.json`):
`traffic[час]` (допущение: утро, обед, вечер, спад к 22:00; среднее по 24 часам даёт «Сегодня») и `air[сезон][час]` (реальный ритм PM2.5 по датчикам OpenAQ).
Выбросы для воздуха считаются по среднесуточному потоку, дорога (задержка, цвета улиц) по выбранному часу. Пресеты UC-08 (18:00) и UC-09 (зимняя ночь, 22:00).
Карточка «Сутки по часам» (site/js/charts.js, `dayline`): 24 прогона локальной JS-модели (`TB.model.simulateLocal`), клик по часу или кнопки «Утро / Обед / Вечер / Ночь» задают `hour`.

## Карта 2GIS и живые данные (объединение с проектом напарника)

От проекта напарника (`Twin_Bishkek_project`) взяты **карта 2GIS с живыми пробками** и **сбор снимков каждые 15 минут**. Модель, город (OSM), объекты и тесты остались наши.

**Как это устроено**

| Что | Где | Что делает |
|---|---|---|
| Карта 2GIS (MapGL) | `site/js/live.js` | слева живые пробки 2GIS, справа наша модель поверх карты (цвета улиц, соты AQI, объекты, события) |
| Замеры пробок | `POST /live/traffic` | пока вкладка открыта, страница шлёт индекс 2GIS видимой области (0–10); не чаще раза в 15 минут на один вид карты |
| Воздух и погода | фоновый поток `live.Collector` | раз в 15 минут берёт Open-Meteo (CAMS + погода) и пишет в SQLite |
| Хранилище | `data/live/twin_live.sqlite3` | две таблицы: `traffic_observations`, `environment_snapshots`. Удалите файл, чтобы очистить историю |
| «Обучение» | `live.learn()`, `GET /live/learned` | сравнивает суточный ритм модели с баллами 2GIS (корреляция) и считает поправку по часам |
| Экспорт для ML | `python -m twin_bishkek.live export` | почасовая таблица воздух + погода + пробки в `data/processed/live_hourly.csv` |

**Ключ 2GIS.** Нужен demo-ключ Map Tiles API (кабинет platform.2gis.com). Два способа:
1. Один раз вставить в поле на сайте (кнопка «Карта 2GIS»): сохранится только в этой вкладке.
2. Задать переменную перед запуском сервера: `$env:TWINGIS_MAPGL_KEY="ваш_ключ"` (PowerShell). Тогда сайт сам подхватит.

В код и в архив ключ не кладём. В кабинете 2GIS ограничьте ключ адресом `http://localhost:8000`.

**Как «обучается» модель.** Для каждого часа берём средний балл 2GIS (только виды «весь город», только будни). Подбираем прямую `балл = a + b · нагрузка_модели`. Если ритм модели совпал с 2GIS (корреляция ≥ 0,5), для часа считается поправка `нагрузка_по_2GIS / нагрузка_модели`, но с усадкой к 1 (чем меньше замеров и дней, тем меньше доверия) и в пределах 0,75…1,25. Поправка включается только после **6+ часов суток по 3+ замера и 4+ разных дней**, и только галочкой «Учитывать замеры 2GIS». По умолчанию выключена: цифры защиты остаются прежними. Если корреляция слабая, поправка не применяется, а на карточке «Что модель узнала от 2GIS» это видно.

**Чего это не делает (и почему).** Замеры приходят только пока открыта вкладка с картой: сервер сам 2GIS не опрашивает и плитки не снимает. Это сделано сознательно: условия 2GIS не разрешают копировать данные. Индекс 2GIS описывает всю видимую область, а не отдельную улицу, поэтому учим только ритм по часам, а не цвет конкретной улицы. Выходные сохраняются, но в поправку пока не идут: в модели профиль только для будней.

**Запуск (всё как раньше, плюс ключ):**
```
$env:TWINGIS_MAPGL_KEY="ваш_ключ"
uvicorn twin_bishkek.api:app --port 8000
```
Отключить фоновый сбор (например, без интернета): `$env:TB_COLLECT="0"` перед запуском.

## Новая дорога через город (тоннель, эстакада, обычная)

Раздел «Новая дорога» в боковой панели (`site/js/roads.js`). Тип, число полос (2/4/6) и стадия («Построена» / «Строится»), затем трасса:
- **кликами по карте** «Если…»: «Нарисовать на карте», точки трассы, двойной клик или «Готово» (Esc — отмена, Backspace — убрать точку);
- **словами**: «тоннель от Джала до Учкуна через центр», «эстакада вдоль Ахунбаева от Джала до Асанбая», «обычная дорога 6 полос из Ак-Ордо в Восток-5». Понимает районы, «центр», стадионы и парки, главные улицы; от/из — начало, до/к/в — конец, через — середина, вдоль/по — по улице.

До 3 дорог в сценарии, они попадают в адрес страницы (`r=`), в сравнение, в «Разбор от модели» и в «План изменений во времени» (вид «Новая дорога», срок по умолчанию: тоннель 36 мес., эстакада 24, обычная 12). В API: поле `roads` у `/simulate`, `/decompose`, `/compare`.

**Как считается** (`P.road` в `model.js` и `ROAD` в `simulator.py`, одинаково; все числа — допущения):

| | Тоннель | Эстакада | Обычная |
|---|---|---|---|
| Ёмкость полосы к обычной улице | ×1,25 (без светофоров) | ×1,25 | ×1,0 |
| Время в пути при той же загрузке | ×0,8 | ×0,8 | ×1,0 |
| Сколько потока забирает у близких параллельных улиц | до 45% | до 40% | до 30% |
| Выхлоп вдоль трассы | нет, 60% выходит у двух порталов | ×0,8 (рассеивается выше) | ×1,0 |
| Пересекаемые улицы | без изменений | без изменений | −10% ёмкости (новые светофоры) |
| Стройка | у порталов −30% проезда, самосвалы, пыль +8% | вдоль трассы −15%, пыль +5% | вдоль трассы −20%, пыль +5% |

Машины переходят на новую дорогу, пока она не заполнится до 90% ёмкости (упрощённое равновесие), плюс 10% новых поездок (индуцированный спрос) и базовое использование 25% ёмкости. Переход считается по длине, которую параллельная улица проходит вдоль трассы, а не по числу её отрезков. Тесты: `tests/test_roads.py`.

## Деревья: какие, сколько, когда вырастут и что дадут

Раздел «Деревья» в боковой панели (`site/js/trees.js`). Порода (платан, карагач, липа, дуб, тополь без пуха, клён, гледичия, сосна, ель тянь-шаньская), сколько штук и где:
- **в районе** (по всему району), **вдоль улицы** (аллея), **нарисовать** линию посадки кликами;
- **словами**: «300 платанов вдоль Чуя», «1000 карагачей в Джале», «сосны от Джала до центра 2 тыс через 10 лет».

Ползунок **«Прошло после посадки» (0–30 лет)** показывает, как деревья растут. До 6 посадок в сценарии; они попадают в адрес страницы (`t=`), в «План изменений во времени» (вид «Посадка деревьев»: возраст считается от месяца посадки, график показывает 10 лет роста) и в API (`trees` у `/simulate`).

**Что считается** (`P.trees` в `model.js` = `TREES` в `simulator.py`):

| Что | Как | Откуда |
|---|---|---|
| Крона через N лет | от саженца 1,5 м до взрослой кроны породы, экспонента со своей скоростью роста; «вырастут» = 80% взрослой кроны | кроны и скорость — допущения (платан 18 м, дуб 16, тополь 12, карагач/липа/клён/гледичия 10, сосна 7, ель 5) |
| Тень | площадь крон, м² | — |
| CO₂ | 1,03 кг CO₂ на 1 м² кроны в год | Nowak et al. 2013: 0,28 кг C/м²/год |
| Пыль PM2.5 | 0,25 г на 1 м² кроны в год; лиственные зимой без листьев (15%), хвойные круглый год | Nowak et al. 2013: 0,13–0,36 г/м²/год |
| Прохлада | −0,3 °C на каждые +10 п.п. площади крон района (летом); в тени до 8 °C прохладнее на ощупь | WRI (мета-анализ) |
| Зелень на жителя | площадь крон / население района → комфорт района | — |
| Воздух (AQI) | кроны снижают PM соты до 5% при полном покрытии | допущение; по Nowak эффект деревьев на концентрацию мал (0,05–0,24%) |
| Полив | молодые (до 3 лет): 100 л в неделю на дерево, водовоз 10 м³; взрослые в основном из арыков (20%) | ~50 л на 3 дня (Бишкекзеленстрой) |
| Пробки от водовозов | только лето, 6:00–11:00, только посадки вдоль дорог: одновременно работает столько машин, сколько нужно на дневные рейсы, каждая занимает полосу (−50% ёмкости) на одном отрезке улицы | допущение |

## Разбор от модели (текстом)

Карточка «Разбор от модели» на экране «Симулятор», под показателями (`site/js/explain.js`). При каждом изменении параметров она пишет:
1. **Итог для города** и **что изменилось и почему**: каждый шаг водопада (автопарк, электромобили, зелень, застройка, события, час) как причина → следствие с числами.
2. **Стройка** (для объектов в стадии «строится»): что происходит в районе **сейчас**, пока идут работы, и что будет **после** окончания (жители, загрузка школ и поликлиник, пробки по сравнению со стройкой).
3. **Что можно сделать**: варианты исправления. Каждый, который задаётся параметрами модели (сдержать автопарк, больше электромобилей или зелени, достроить парковки, строить по очереди, не перекрывать улицу, расширить магистраль), сначала прогоняется через модель. Показываются только те, что реально помогают, с результатом и кнопкой «Применить». Советы, которых в модели нет (школы, шаттлы на матч, отопление), помечены «в модели не считается».

Тексты собираются по правилам из чисел модели, без нейросети: одинаковый сценарий всегда даёт одинаковый разбор.

## План изменений во времени

Раздел «План изменений во времени» на экране «Симулятор». Вы записываете, что и когда происходит, а ползунок по месяцам показывает город в выбранную дату: пока идут работы и после них.

**Что можно записать**
- **Строительство объекта:** ЖК, ТЦ, парк или аттракционы. Поля: название, район, вместимость (семьи / торговая площадь м² / площадь парка га / посетителей в день), **парковочные места**, этажи, заметка, месяц начала и месяц окончания.
- **Перекрытие улицы** и **закрытие моста** на период «с месяца … до месяца …».
- **Новая магистраль** (расширение улицы): пока идут работы полоса закрыта, после окончания пропускная способность +50%.

**Как это считается.** Для каждого месяца план превращается в обычный сценарий модели: объект в окне работ в стадии «строится» (поток ×0,6, потеря пропускной способности рядом, пыль), после окончания «построен» (жители, поток, зелень). Перекрытия действуют только внутри окна. Дальше те же расчёты, что и везде. Галочка «Показывать этот месяц на картах выше» переносит выбранный месяц на карты, кнопка «Показать по месяцам» проигрывает план.

**Как вместимость и парковки влияют на расчёт**

Нормы парковок взяты из **СН КР 30-01:2020** «Планировка и застройка городов и населённых пунктов городского типа», приложение З (обязательное), кроме отмеченных допущений.

| Тип | Эталон модели | Нужно парковочных мест | Откуда |
|---|---|---|---|
| ЖК | ~1140 семей (4000 жителей, 3,5 человека на семью) | жители × 0,8 м² / 18 м² ≈ 1 место на 22,5 жителя | прил. З, примечание 1; 3,5 чел. на семью — допущение |
| ТЦ | 20 000 м² | 1 место на 75 м² торговой площади | прил. З, п. 4.2 (70–80 м²) |
| Парк | 10 га | 15 мест на га | допущение: в нормах числа нет (отсылка к разделу 9) |
| Аттракционы | 5000 посетителей в день | 1 место на 9 одновременных посетителей, одновременно ~30% дневных | прил. З, п. 5.6 (8–10); 30% — допущение |

Масштаб объекта `n` = вместимость / эталон (дробный: 0,3 ЖК, 1,05 ЖК). Если указанных парковок меньше нужного, считаем дефицит. Машины выдавливаются на соседние улицы: коэффициент нагрузки `tk = 1 + 0,5 · дефицит` (до ×1,5, допущение). Если парковки не указаны, дефицит не считается. Норма для ЖК — нормативный минимум; реальная автомобилизация в Бишкеке может быть выше (см. `docs/ИСТОЧНИКИ_И_ОГРАНИЧЕНИЯ.md`).

**Ограничения.** Модель одновременно учитывает одно перекрытие улицы, один мост и одну новую магистраль: при пересечении работ побеждает начатая позже, об этом написано под графиком.

**Где хранится план.** На сервере, в `data/live/plan.json` (`GET /plan`, `PUT /plan`; путь меняется переменной `TB_PLAN_FILE`), поэтому все, кто открыл сайт с этого сервера, видят один и тот же план. Сайт перечитывает его при открытии и при возврате на вкладку. Копия лежит и в браузере (localStorage): без сервера план работает как раньше, только локально, а при первом подключении к серверу с пустым планом браузер отдаёт ему свою копию. Правки с двух компьютеров одновременно не сливаются: сохраняется последняя.
